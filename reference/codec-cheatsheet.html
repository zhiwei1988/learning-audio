编码 / 带宽 / 时延速查

选编码或拆音质卖点时扫这一页。数据源：Fraunhofer AES-122、ITU-R BS.2161、ONVIF 规范。

一句话

带宽决定「听不听得清」，时延决定「能不能对讲」，两者方向相反。所以单向路与对讲路应该用不同的编码。

选型表

编码 带宽 算法时延 码率 用在哪
G.711（µ-law / A-law） 300–3400 Hz @8 kHz ≈ 0（逐样本压扩） 64 kbps 对讲默认；互通性最好
G.726（ADPCM） 300–3400 Hz @8 kHz 极低 16–40 kbps 带宽受限的对讲
AAC-LC 全带 ≥ 55 ms @48 kHz 32 kbps 起，≈64 kbps 近透明 只用于单向监听 / 录像
AAC-LD 全带 低至 20 ms（1 490 samples ≈ 31 ms 典型） 48 kbps/声道起 双向且要音质
AAC-ELD 全带 15 ms @64 kbps 比 AAC-LD 省 25–33% 双向，音质 + 低码率

锚点：交互式双向通信的系统时延建议 ≤ 50 ms（Fraunhofer）。编码只是其中一段，别拿它当总数。

采样率砍掉了什么

频段装的是什么8 kHz 采样下
85–255 Hz基频 F0（男/女声）保留
300–3400 Hz元音与共振峰（可懂度主体）保留
4–8 kHz齿擦音 /s/ /f/ /sh/整段丢失
8 kHz 以上空气感 / 自然度整段丢失
症状识别 整句能懂、念姓名/车牌/数字出错 = 带宽问题（4 kHz 以上被切），不是 SNR、AEC 或 AGC 问题。 门铃/访客对讲的高频用例恰好全在这里。
反直觉陷阱 AAC-LC 帧长固定 1024 个采样，不是固定毫秒数。 为省带宽把采样率从 48 kHz 降到 16 kHz → 音质降了，时延涨到约三倍。

ONVIF 对音频承诺了什么

  • Profile Feature Overview 里 Audio Streaming / Audio Output Streaming 全部是 C = Conditional，不是 M。ONVIF 不要求摄像机有音频。
  • 唯一约束（脚注 6）：「If supported, Device/client must support at least one of G.711 and AAC」。
  • AudioEncoderConfiguration 只有 Encoding（G.711/G.726/AAC）、Bitrate（kbps）、SampleRate（kHz）、SessionTimeout。
  • ONVIF 不区分 AAC-LC / LD / ELD——枚举里只有一个「AAC」。要低时延档必须在 ONVIF 之外单独确认。
  • 走自家 App 私有协议的对讲不受这套枚举限制，可以直接上 AAC-LD / Opus。

木桶效应：链上每一环的采样率

麦克风频响 → 算法带宽 → 编码采样率 → 网络 → 解码 → 喇叭频响。任一环是 8 kHz，整条链就是 8 kHz。

断点表现
断在编码（最常见）宽带麦 + G.711 → 前面全白做
断在算法（最隐蔽）AAC@48k，但 AEC/NS 内部跑 16 kHz，或 NS 把高频当噪声削了
断在器件麦或喇叭本身高频就滚降（见 麦指标速查）

评审杀手锏一句话：「从麦克风到 RTSP 输出，这条链上每一环的采样率分别是多少？」 答不上来 = 中间一定有一环在偷偷降采样。

规格书写法

  • 分路写：监听/录像路与对讲路分别指定编码。
  • 写全三元组：编码 + 采样率 + 码率。只写「支持 AAC」等于没写。
  • AAC 写明 profile：LC / LD / ELD。
  • 时延：报 mouth-to-ear 总时延与测法，不是编码时延。
  • 可懂度：用念姓名 / 车牌 / 数字串的错误率验收，直接测 4 kHz 以上那段。
  • ONVIF：写「Profile T 且支持音频流，G.711 与 AAC 至少其一」。
