算力与预算速查

评审前扫这一页，或者打印带进会议室。数据源：TI TIDUE77 Table 5、TMS320C5517 datasheet、TI SPRABN1 Table 1、IJRRAS 2011（NLMS 复杂度）。

一句话

按峰值配，不按平均配；先找出最紧的那本账，再决定往哪使劲。算力是按档买的，跨过一档才有钱可拿。

四条记账规矩

规矩为什么
1. 只认峰值 音频按 10 ms 一帧交货，算不完就是丢帧（一声「咔」）。峰值 ÷ 平均 = 1.15×，而峰值出现在双讲、回声路径突变这些最要命的时刻。
2. 模块之和 ≠ 系统总量 框架、驱动、I/O 缓冲不属于任何模块，却占了内存的 47 %。把三个模块加起来当预算，会漏掉接近一半。
3. 内存要拆三项 程序段（共用一份）+ 数据段 + 实例数据 × 路数。实例数据随尾长、随通道数乘出来，是最常漏的一项：HD AEC 的实例数据 67 KB，比它的代码段还大。
4. 留 20 % 余量 工程惯例，不是标准。写进规格书要注明是谁定的、留给什么用。200 MIPS 的芯片，可用的是 160。

尾长 → 占用（外推规则）

AEC 的算力几乎全在自适应滤波器上，所以 MIPS 与实例内存都近似正比于尾长。 自查用的估算式（NLMS 每样本 3N+1 次乘法）：

步骤算式128 ms @16 kHz
抽头数尾长(s) × 采样率2 048
每样本乘法3N + 16 145
每秒乘法(3N+1) × 采样率98.3 M
对照实测估 98 vs 实测 113.1差 15 %（双讲检测等附加件）

外推按线性走是保守上界：频域实现的成本约 O(L log L)，实际会比线性更省。 预算外推一律往坏的方向取整。

要数据时的四句话

  • 「照 TIDUE77 Table 5 的格式给：逐模块、峰值列、实例数据列，在我们的采样率和帧长下。」
  • 「尾长给三个点（32 / 64 / 128 ms）的曲线，不要单点——我要自己插值。」
  • 「这份数据是在什么条件下测的？视频满码率和 AI 检测同时开了吗？」
  • 「丢帧计数（xrun / frame overrun）是多少？只要不是 0，平均占用多低都不算数。」

自测最坏用例

  • 双讲 + 高噪 + 视频满码率 + AI 检测全开，连续 ≥30 分钟。
  • 记两个数：CPU 占用峰值（不是 top 的平均）与丢帧计数。
  • 验收线：峰值 ≤ 可用算力的 80 %，丢帧计数 = 0。
  • 内存按 程序 + 数据 + 实例 × 路数 + 框架缓冲 四项分别报。

默认追问

  • 「这是平均还是峰值？」——对任何算力数字的第一反应。
  • 「先撞的是哪面墙？算力、内存、功耗、BOM，四本账各用了百分之多少？」
  • 「尾长配了多少？现场那条回声路径实际多长？」（接第 6 课）
  • 「这颗芯片的频率档位表长什么样？我们现在踩在哪一档？」
  • 「跑在主 SoC 上的话，视频拉满时余量还剩多少？谁负责这个风险？」
