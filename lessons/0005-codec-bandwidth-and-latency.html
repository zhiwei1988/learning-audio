Lesson 0005 · 约 20 分钟

「高清拾音」断在哪一环

采样率是一堵墙，编码时延是另一堵。这一课让你能判断一条音质卖点是真是假，并且知道为什么整个安防行业明知 G.711 难听还在用它。

与 Mission 的关系
前四课都在讲「怎么把声音采好、处理好」。但信号最后要穿过编码器才能到用户耳朵。 这一环有两个硬约束——带宽与时延——而且它们互相打架。 能把这层讲清楚，你才能判断「高清拾音」「高清对讲」这类卖点到底成不成立，以及该往哪投钱。

本课技能

拿到一份编码规格（G.711 / G.726 / AAC、采样率、码率）， 能说出它砍掉了哪一类信息、吃掉多少时延预算，并据此判断该给单向监听和双向对讲分别配什么编码。

一、采样率是一堵墙

采样率决定能记录的最高频率上限（奈奎斯特频率 = 采样率 ÷ 2）。安防行业的 G.711 / G.726 惯例是 8 kHz 采样（VIVOTEK）， 理论上限 4 kHz，实际电话带是 300–3400 Hz。 对照 ITU-T G.722 定义的宽带语音是 50–7000 Hz。

问题不在于「音质差一点」，而在于被切掉的是一类特定的信息。点下面的按钮看：

这才是重点 /s/ /f/ /sh/ 这类清擦音的能量主要在 4 kHz 以上，在 8 kHz 采样下被整段切掉。 元音全部活着，所以句子「大致能懂」——但区分 s 和 f 的信息基本没了。 产品上的表现就是：连续说话听得懂，念姓名、车牌、数字、验证码时开始出错。 这也是电话里报名字要一个字一个字拼的原因。

门口场景里这恰恰是最高频的用例——「你是哪位？」「快递单号是多少？」「车牌尾号几号？」。 所以「8 kHz 够用了，反正能听懂」这个论断，在监控摄像机上成立，在门铃/访客对讲上不成立。

二、时延是另一堵墙，而且方向相反

直觉是「上 AAC 音质更好」。但编码器要攒够一帧才能开始编，这个等待就是算法时延，无法用更快的 CPU 消除。

Fraunhofer（AAC 的发明方）在 AAC-ELD 的论文里说得非常直接： 「While AAC-LC provides high audio quality, its algorithmic delay of at least 55 ms (1024 samples per frame, 48 kHz) is clearly too high for bi-directional communication.」 同一段还给了行业阈值：「Generally, the system delay for interactive two way communication should not exceed 50 ms.」 （AES 122nd Convention · Enhanced Low Delay AAC）

编码 带宽 算法时延 码率 适合
G.711 300–3400 Hz ≈ 0（逐样本压扩，一个采样） 64 kbps 双向对讲、最大互通性
G.726 300–3400 Hz 极低（ADPCM 逐样本） 16–40 kbps 带宽受限的对讲
AAC-LC 全带（取决于采样率） ≥ 55 ms @48 kHz 32 kbps 起可用，≈64 kbps 近透明 单向监听 / 录像回放
AAC-LD 全带 低至 20 ms 48 kbps/声道起 双向，且要音质
AAC-ELD 全带 15 ms @64 kbps 比 AAC-LD 省 25–33% 双向，音质 + 低码率

AAC-LD / ELD 时延数据：ITU-R Report BS.2161 表 2 （AAC-ELD 15 ms vs AAC-LD 20 ms @64 kbit/s；AAC-LD 整体算法时延 1 490 samples ≈ 31 ms）。

一个反直觉的陷阱 AAC-LC 的帧长固定是 1024 个采样——不是固定的毫秒数。 采样率越低，同样的帧数换算成时间越长。 也就是说，为了省带宽把 AAC 从 48 kHz 降到 16 kHz，音质降了，时延反而涨到约三倍。 这是「既要省带宽又要上 AAC」时最容易踩的坑。

三、所以行业用 G.711 不是懒

G.711 是 8 kHz 采样、8 bit 对数压扩、64 kbps 的逐样本编码。它没有「帧」的概念，所以算法时延约等于零。 安防行业选它，是在拿音质换时延 + 简单 + 互通性——对讲体验里时延的权重远高于音色。

把它接回第 3 课：全双工对讲的总时延预算里，编码只是其中一段。 算上采集缓冲、AEC/NS/AGC 的处理块、网络抖动缓冲、解码、播放缓冲—— Fraunhofer 那条「交互式双向通信系统时延不应超过 50 ms」的线，光是 AAC-LC 一个编码器就已经吃穿了。 整张账怎么拆、每一项典型多少、哪一项才值得动，见 第 6 课 · 时延预算。

最有用的产品结论 一台机器可以对两条路用不同的编码。 单向监听 / 录像回放 → 上 AAC（时延不敏感，音质是纯收益）； 双向对讲 → G.711，或者上 AAC-LD / ELD（如果 SoC 与对端支持）。 很多产品讨论一上来就问「我们该用 G.711 还是 AAC」——这问题本身就问错了，它不是二选一。

四、ONVIF 对音频到底承诺了什么

规格书上常见「符合 ONVIF Profile T」。对音频而言，这句话的实际保证比想象中弱得多。

在 ONVIF Profile Feature Overview 的功能矩阵里， Audio Streaming（G.711 / AAC / G.726）与 Audio Output Streaming 全部标记为 C = Conditional（条件性）， 不是 M = Mandatory。也就是说 ONVIF 根本不要求摄像机有音频。 只有一条约束（脚注 6）：「If supported, Device/client must support at least one of G.711 and AAC」—— 如果支持，那么 G.711 和 AAC 至少要支持其一。

配置层面，ONVIF Media Service 的 AudioEncoderConfiguration 只有四个可谈的字段： Encoding（G.711 / G.726 / AAC）、Bitrate（kbps）、 SampleRate（kHz）、SessionTimeout。 注意：ONVIF 不区分 AAC-LC 与 AAC-LD/ELD——枚举值只有一个「AAC」。 要低时延 AAC，得在 ONVIF 之外单独跟供应商确认 profile。

编码规格 · 可直接抄进需求文档

  • 分路指定：监听/录像路与对讲路分别写编码，不要合并成一行。
  • 写全三元组：编码 + 采样率 + 码率。只写「支持 AAC」等于没写。
  • AAC 必须写明 profile：LC / LD / ELD。ONVIF 枚举里区分不出来，要单独问。
  • 时延验收：报 mouth-to-ear 总时延（不是编码时延），并写明测法与网络条件。完整条款见第 6 课。
  • 可懂度验收：用念姓名 / 车牌 / 数字串的错误率，而不是「听着清楚」。这直接测 4 kHz 以上那段。
  • ONVIF 措辞：写「Profile T 且支持音频流，G.711 与 AAC 至少其一」——只写 Profile T 不构成音频承诺。

五、木桶效应：卖点会断在最短的那块

带宽是一条链：麦克风频响 → 算法带宽 → 编码采样率 → 网络 → 解码 → 喇叭频响。 任何一环是 8 kHz，整条链就是 8 kHz。常见的断点：

断在编码

  • 宣传「高清拾音」
  • 麦是宽带 MEMS
  • 但编码是 G.711 @ 8 kHz

→ 最常见。前面全白做

断在算法

  • 编码上了 AAC @ 48 kHz
  • 但 AEC/NS 内部跑 16 kHz
  • 或 NS 把高频当噪声削了

→ 隐蔽。要看算法采样率

问供应商的那一句话：「从麦克风到 RTSP 输出，这条链上每一环的采样率分别是多少？」 能立刻答上来的，说明这条链真的有人负责；答不上来的，基本可以确定中间有一环在偷偷降采样。
